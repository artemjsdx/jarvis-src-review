# CI и эмулятор — как устроено, как запускать, как читать отчёт

Владелец на мобильном интернете, ADB к телефону выключен. Поэтому проверка приложения делается на GitHub-зеркале
(`artemjsdx/jarvis-android`, приватное): там собирается APK, гоняются JVM-тесты и поднимается Android-эмулятор, который
управляется через MCP-мост так же, как телефон.

## 1. Что запускается

Файл `.github/workflows/ci.yml`, на каждый push в `master` и по запросу (`workflow_dispatch`):

| job | что делает | время |
|---|---|---|
| `apk` | три подписанных APK: мост для телефона (arm64), эмуляторный мост (x86_64, `mcp.allowDestructive=true`, `ui.glass=off`), отладочный APK. Публикует их как релиз `ci-apk` | ~1,5 мин |
| `tests` | все JVM-тесты `tools/run-tests.sh` (876 тестов) | ~5 мин |
| `emulator` | только с `[emu]` в сообщении коммита или с `-f emulator=true`. Android 14 x86_64, KVM, `cores 2`, `ram 3072M`. Публикует `emulator-report.zip` как релиз `ci-emulator` | ~8–10 мин |

Релизы вместо артефактов: хранилище артефактов аккаунта заполнено. Для веток, отличных от `master`, теги получают суффикс
имени ветки (`ci-emulator-ci1`).

Секреты репозитория: `JARVIS_KEYSTORE_B64`/`JARVIS_KEYSTORE_PASS` (подпись), `JARVIS_BRIDGE_B64` (provisioned-мост:
токен и нейтральные настройки, без ключей), `OPENROUTER_KEY` (необязательный; без него живой LLM-тест пропускается).

## 2. Как запустить

С рабочей машины агента (нужен `~/jarvis-keys/github.token` и `github.repo` в домашнем каталоге Termux):

```
export HOME=/data/data/com.termux/files/home
source tools/ci/gh.sh
export CI_BRANCH=ci1
ci_push HEAD:refs/heads/ci1          # сначала сканер секретов; пушить только ветку агента
ci_run -f emulator=true              # запуск workflow на ветке ci1 с эмулятором
ci_watch 25                          # ждать завершения; печатает статус jobs
ci_fetch ci-emulator build/ci-emu    # скачать отчёт эмулятора (для ветки ci1: тег ci-emulator-ci1)
```

Токен никогда не печатается: функции `gh.sh` передают его только через окружение.

Отчёт распаковывается так: `cd build/ci-emu && unzip emulator-report.zip`. Внутри `emu/`:

* `summary.txt` — первым делом. Строки: устройство, установка, старт, здоровье моста, `jv-check`, `mcp-smoke` (pass/fail/skip),
  живой LLM-тест, проходы по экранам с `ui.glass=off` и `full` (число кадров, доля рывков), headless-окно, FATAL в logcat, итог.
* `smoke.txt` и `smoke/mcp-report-*.md` — каждый сценарий: `ok`/`FAIL` и причина; `SKIP` с причиной (нужен ключ, флаг, засеянные ходы).
  Снимки сценариев лежат в `smoke/shots/`. Экранные снимки чата: `ci_chat_screens-*.jpg`.
* `glass-off/`, `glass-full/` — `live_<экран>.png` (снимок окна через мост), `adb_<экран>.png` (adb screencap, без моста),
  `tree_<экран>.json` (дерево видов), `frames.jsonl` (`perf_frames` на переходах между экранами), `settle.txt` (загрузка CPU
  перед снимком).
* `llm.json` — живой тест: ответы, вызовы инструментов, тайминги трассы, стоимость (дельта использования ключа), признак
  «ключ не попал в журнал».
* `logcat.txt`, `journal_warn.json`, `app_health.json` — для разбора падений.

Важно: `ci-emulator` публикуется в конце job, поэтому пока run идёт, отчёта нет.

## 3. Что делается, чтобы эмулятор был пригоден

* **Программный GPU.** `-gpu swiftshader_indirect`: кадры приходят медленно. Размытие «стекла» (`ui.glass=full`) на нём
  занимает секунды на кадр. Поэтому сборка эмулятора поставляется с `ui.glass=off`, а проход `full` выполняется последним:
  если он вызовет ANR, приложение перезапускается (`ensure_app` в `emulator-smoke.sh`).
* **Системные окна.** `hide_error_dialogs=1`, `CLOSE_SYSTEM_DIALOGS` перед каждым снимком. Окно «не отвечает» не
  закрывается автоматически: кнопка «Закрыть приложение» завершила бы процесс.
* **Тишина перед снимком.** `tools/ci/wait-idle.py` ждёт, пока загрузка CPU эмулятора не упадёт ниже 25 % (до 12 с).
* **Деструктивные инструменты** (`sessions_delete`, `chat_seed`, `secrets_set`) — только в эмуляторной сборке.
  Телефонная сборка их не получает; соответствующие сценарии на телефоне пишут причину пропуска.
* **Засев чата** (`chat_seed`): элементы разных видов добавляются без модели, поэтому экраны (короткий обмен, длинный ответ,
  ошибка, три параллельных действия свёрнутое и развёрнутое, десять действий, меню сессий, вложения, светлая тема)
  снимаются детерминированно. Сценарии: `tests/mcp/ci_chat_screens.json`.
* **Живой LLM-тест** (`tools/ci/llm-roundtrip.py`): ключ OpenRouter передаётся в app через `secrets_set`, модель
  `deepseek/deepseek-v4.1-flash`, один ход без инструментов и один ход с инструментом (`note_create`). Ключ читается только
  из переменной окружения; проверяется, что он отсутствует в журнале. Бюджет 0,02 USD на прогон.

## 4. Как читать отчёт

1. `summary.txt`: есть ли `result: PASS` и `FATAL EXCEPTIONs in logcat: 0`. Падение моста — это FAIL.
2. `smoke/mcp-report-*.md`: строки `FAIL` с текстом ошибки. `SKIP` — не ошибка; причина указана.
3. Снимки: сравнивать `live_*.png` (окно моста) с `adb_*.png` (то, что видит система). Расхождение означает, что
   мост снимает не тот экран (как было с наложенными экранами в первом прогоне).
4. `frames.jsonl`: `jankPct` и `p90Ms` на переходах. Мало кадров (несколько на переход) — это свойство программного GPU,
   а не регрессия; сравнивайте проходы между собой.

## 5. Известные ограничения

* **Программный GPU** (swiftshader). Цифры кадров не переносятся на телефон: там аппаратный GPU и реальное размытие.
  Измеряются только относительные величины (что дороже: `full` или `off`) и корректность экранов.
* **API 34 против Android 16** на телефоне владельца. Поведение `ui.glass` (API 31+), системных диалогов и разрешений
  может отличаться.
* **Нет микрофона и звука.** Голосовые сценарии (`voice_*`, `wake`, `stt`) на эмуляторе пропускаются либо работают через
  файлы. Сценарии `tts_*` с ElevenLabs пропускаются без ключа (`requires: key:elevenlabs`).
* **Сеть эмулятора**: исходящие запросы идут с раннеров GitHub; отличаются от телефона.
* **JVM-тесты с настоящим adb** (`AdbInteropTest`) иногда падают на раннере и локально без `HOME`
  (нужен ключ `~/.android/adbkey`); на master проходили.
* **Стоимость LLM-теста** показывается как дельта использования ключа. Ключ общий с владельцем, поэтому дельта
  приблизительная; при дешёвой модели она ниже 0,00005 USD и печатается как 0,0000.
