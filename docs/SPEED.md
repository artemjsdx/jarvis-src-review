# SPEED — скорость голосовой цепочки: трассировка, замеры, выводы (P-01, P-05, P-09)

Все числа ниже — «стенд (vivo I2407)»: Wi-Fi (wlan0, сеть 10.61.19.0/24), выход в интернет из Беларуси, 2026-10-29 примерно 02:40–03:55 (UTC+3).
Это не замеры на целевом Realme и не на мобильной сети. Скрипты лежат в `tools/bench/`, их можно перезапустить и получить свои числа.

## 1. Трассировка хода (P-01)

Класс `app.jarvis.core.trace.TurnTrace` — запись одного хода (голос или текст) на монотонных часах (`System.nanoTime`),
`TraceStore` хранит последние 100 завершённых ходов в памяти и добавляет по одной JSON-строке на ход в
`filesDir/trace/turns.jsonl` (не больше 2 МиБ: при превышении отбрасывается старая половина файла).
По завершении хода в журнал пишется одна строка категории `performance` (в приложении категория называется именно так, не `perf`):
`Ход 11,1 с до звука: STT 2,4 | LLM 6,4 | TTS 1,6 | пауза 0,7`, полная раскладка — в `details` записи журнала.

### API для MCP-моста
* `TraceStore.global().recent(int n)` → `List<JSONObject>`, самые новые n завершённых ходов, старые первыми (то же, что хочет `perf_turns`).
* `TraceStore.global().current()` — открытый ход или `null`.
* `TraceStore.install(File dir, Listener)` вызывается один раз в `AgentRunner` (ему принадлежит `filesDir/trace`).

### Схема JSON одного хода
```
{ "id": 2, "source": "voice"|"text", "start_ms": <epoch ms создания>, "complete": true|false,   // false: ход вытеснен следующим
  "marks": { "<имя>": <мс от самой ранней метки хода>, ... },
  "spans": { "<имя>": <мс>, ... },
  "stt":  { "purpose": "wake"|"command", "provider", "audio_ms", "pcm_bytes", "attempts", "chars" },
  "llm":  { "provider", "model_requested", "model", "calls", "prompt_chars", "tool_specs", "tokens_in", "tokens_out", "tokens_cached", "headers_ms" },
  "tts":  { "provider", "chars", "pieces", "cache_hit"? },
  "turn": { "run_id" },
  "tools":[ { "name", "start": <мс от начала>, "ms": <длительность, -1 если не закончился>, "ok" } ],
  "summary": "Ход 2,5 с до звука: STT 0,9 | LLM 0,5 | TTS 0,4 | пауза 0,7" }
```
Метки (`marks`), первое вхождение, если не сказано иное:

| метка | где ставится |
|---|---|
| `speech_end` | оценка конца голоса: момент выдачи фразы сегментером минус `endSilenceMs` (650 мс); у обрезанной по длине фразы — момент выдачи (`VoiceController.markUtteranceEnd`) |
| `speech_end_detected` | сегментер решил, что фраза кончилась (`speech_end` + 650 мс) |
| `wake_detected` | слово «Джарвис» найдено в распознанном тексте (`screenForWake`) |
| `stt_start`, `stt_final` | вокруг цикла провайдеров STT в `VoiceController.transcribe` (последнее вхождение: после голой фразы-обращения команда перезаписывает) |
| `submit` | `AgentRunner.submit` (у текстового хода это начало отсчёта) |
| `llm_request` | `onStep` первого шага агента (до сборки запроса, разница с отправкой — миллисекунды) |
| `llm_first_token` | `llm_request` + `LlmResult.firstDeltaMs` первого шага (любая дельта: текст или вызов инструмента) |
| `llm_first_text` | первая текстовая дельта любого шага |
| `llm_done` | конец последнего шага (последнее вхождение) |
| `tts_request` | первый кусок текста поставлен в очередь озвучки (`SpeechService.speak`) |
| `tts_synth_start` | рабочий поток плеера начал синтез этого куска (позже `tts_request`, если ещё играет предыдущий) |
| `tts_first_audio` | первый байт аудио от провайдера (или из кэша) прошёл в приёмник (`GuardSink.write`) |
| `play_start` | `SpeechOut.onFirstAudio`: первый слышимый (> 1 % шкалы) отсчёт передан в AudioTrack |
| `play_end` | озвучка затихла (`onSpeakingChanged(false)`, последнее вхождение) |
| `agent_done` | конец запуска агента |

Производные (`spans`, мс): `endpoint` (speech_end→speech_end_detected), `stt`, `stt_to_llm`, `llm_ttft` (до первого токена), `llm_first_text`, `llm_total`,
`tts_queue`, `tts_ttfa` (tts_synth_start→tts_first_audio), `tts_total` (tts_request→tts_first_audio), `play_gap` (tts_first_audio→play_start),
`text_to_tts`, `to_sound` (speech_end или submit → play_start, а без озвучки → первый текст/конец запуска), `total`, `tools` (сумма длительностей).

Ход завершается, когда агент закончил И озвучка затихла (или озвучки не было). Если следующий ход начинается раньше, предыдущий закрывается с `complete:false`.
Голос → агент: `VoiceController` кладёт трассу в `TraceStore.handoff` прямо перед `j.submit`, `AgentRunner.submit` её забирает (источник `voice`, не старше 60 с).

### Что НЕ размечено точно
* `bytes uploaded` для STT: записывается размер PCM (`pcm_bytes`), а не реально отправленных байт (WAV = PCM + 44 байта; у Google FLAC меньше) — `SttResult` не несёт числа, а провайдеры не мои.
* `play_start` — момент записи в AudioTrack, а не звук из динамика: добавьте предзаполнение ≤ 120 мс (`PcmTrack.startThresholdMs`) и задержку аудио-тракта устройства (не измерялось: звук запрещён).
* `speech_end` — оценка (выдача фразы минус 650 мс), а не событие VAD.
* Сменный провайдер: у `llm.provider` пишется провайдер из настроек (`openrouter`), у OpenRouter-маршрутизации реальный апстрим (Relace/Wafer/…) в трассе не виден.

## 2. Чистка текста для озвучки (P-05, P-09)

`SpeechText.clean(text[, opts])` и `SpeechText.forSpeech` (clean + числа/даты/единицы) применяются ко всем запросам озвучки до провайдера и до ключа кэша
(`SpeechService.speak/prepareText/speakWith/prewarm`). Правила:
* «…», `...`, `. . .`: внутри предложения → запятая («Ну... не знаю» → «Ну, не знаю»), перед новым предложением и в конце → точка, после знака/в начале → убирается;
* markdown: `**`, `*`, `_`, `~~`, обратные кавычки, заголовки, маркеры списков и нумерация (пункт получает точку в конце — пауза), цитаты, таблицы (`|` → запятая), `---`, ссылки `[текст](url)` → текст, картинки удаляются, `[1]` удаляются;
* блоки кода ```…``` (в том числе оборванные) удаляются целиком; произносится «код» только если задана настройка `tts.codeMarker`;
* эмодзи, символы категорий So/Sk, форматные и управляющие знаки удаляются (`°`, `№`, `₽`, `$`, `%` остаются); голые URL → «ссылка» (хвостовая пунктуация сохраняется);
* повторы `!!!`, `??`, `?!` → один знак, `,,`, `,.` и т. п. схлопываются, `--` → « — »;
* если после чистки нет ни одной буквы/цифры, результат пустой и в провайдер ничего не уходит (`SpeechService.speak` пропускает такие куски; `SpeechStreamer` не выдаёт их и не озвучивает код между ```).

Проверка на реальном Edge (скрипт `tools/bench/edge_dots.py`, один сокет): для текста из одной пунктуации (`...`, `…`, `. . .`, `!!!`, `?!`) сервис отвечает без единого аудиокадра за 0,7–1,4 с
(приложение получало `NO_AUDIO` «Служба Edge не вернула звук» и тост об ошибке), а `Подожди...` и `Подожди.` дают одинаковые 11232 байта аудио — точки Edge не читает.
Значит «точки по 5–10 с» на Edge воспроизвести не удалось: причина там — не озвучивание точек, а цепочка (сбой одного куска + новое соединение 2–5 с на каждый следующий).
Другие провайдеры цепочки (gtts, Silero) на точки не проверялись. Тесты: `SpeechTextTest` (≈190 строк таблиц, длинный смешанный ответ, идемпотентность).

## 3. Edge TTS: повторное использование соединения (P-05)

Сервис принимает несколько `speak` на одном WebSocket (проверено: `tools/bench/edge_reuse.py`, N=10, python `websockets`, Termux):

| режим | до первого аудиокадра от отправки | всего до `turn.end` | соединение |
|---|---|---|---|
| новое соединение на фразу | 462–3678 мс, медиана ≈ 1075 | медиана 1390 | TCP+TLS+WS **1812–5514, медиана 2812 мс** → до звука медиана **3740 мс** (2274–6865) |
| один сокет, speech.config на каждую фразу | медиана 585 (410–3927), n=9 | медиана 992 | один раз 3457 |
| один сокет, speech.config один раз | медиана 481 (309–916), n=9 | медиана 826 | один раз 2637 |

Простой сокета: ответил после паузы 5, 15, 30 с; после 40, 45, 50, 55, 60 с — `ConnectionClosedError` (сервер закрывает молча). Поэтому в `EdgeTts` простаивающий сокет живёт 20 с.

Реализация (`EdgeTts`): пул до 2 простаивающих сокетов, ключ — формат вывода; сокет возвращается в пул только после чистого `turn.end` (не отменён, не оборван; «нет аудио» — сокет цел);
сокет старше 20 с не берётся, лишние закрываются и по таймеру; мёртвый пул-сокет (закрыт сервером/молчит > 6 с до первого кадра) → одна прозрачная повторная попытка на новом соединении, пока в приёмник не ушёл ни один байт;
`prewarm()` открывает сокет заранее, запрос, пришедший во время прогрева, присоединяется к нему (не открывает второй); `closeIdle()`; настройка `keepAlive=false` отключает пул.
Прогрев: `SpeechService.warmUp()` вызывается в момент конца фразы пользователя (push-to-talk), при найденном «Джарвис» и при старте запроса, если ответ будет озвучен.
Тесты `EdgeTtsPoolTest` (9): общий сокет, `keepAlive=false`, мёртвый сокет, просроченный сокет, отмена, «только пунктуация», параллель, прогрев, `closeIdle`.

Проверено на настоящем рантайме Android (ART, свой TLS-стек, `SpeedCheck`, 8 фраз, тот же код приложения, MP3 декодируется настоящим MediaCodec, звук не выводится):

| режим | первый аудио-байт (мс) | весь синтез (мс) |
|---|---|---|
| новое соединение на фразу | медиана **2771** (2165–6278) | 3497 |
| пул (первая фраза платит соединение) | медиана **836** (671–2495); фразы 2–8: 671–1626 | 1420 |
| прогретый сокет | медиана **600** (446–861) | 1049 |

Воспроизведение начинается с первых кадров: от первого MP3-байта до первого декодированного PCM в MediaCodec 31–154 мс (медиана ≈ 55–70), а весь синтез кончается на 0,4–0,9 с позже первого байта.
В голосовом прогоне (раздел 5) `tts_first_audio → play_start` = 90–100 мс.

Кусочки одного ответа озвучиваются последовательно одним рабочим потоком `SpeechPlayer` (по коду): синтез куска N+1 начинается только после того, как закончилось проигрывание куска N,
то есть между предложениями есть пауза ≈ времени до первого аудио (0,6–0,9 с с пулом, 2–5 с без него). Предзагрузка следующего куска не делалась (файл плеера не мой) — это следующий шаг.

## 5. Голосовые ходы целиком (настоящая цепочка, без микрофона и без звука)

`app/src/e2e/java/.../SpeedE2E` (вместе с `SilentOut`): записанная фраза → `FakeMic` → Segmenter → облачный STT (wake: Google Speech v2) → обращение → агент (OpenRouter `inception/mercury-3`, настоящие инструменты) →
`SpeechText` → Edge TTS → декодирование MediaCodec; вместо динамика `SilentOut` (то же событие «первый слышимый отсчёт», ожидание длительности аудио). Запуск — через `adb shell` на телефоне (`app_process` из Termux-proot не виден).

| ход | до звука | распределение |
|---|---|---|
| «Джарвис, что ты сейчас делаешь?» (прямая команда, без LLM) | 5,4 с | пауза-тишина 0,65 + STT 2,7 + TTS 1,9 (сокет Edge только открывался: прогрев начался за 37 мс до запроса; после этого прогона добавлено присоединение запроса к идущему прогреву) |
| «Джарвис, создай заметку…» (LLM, 2 шага, инструмент `note_create` 27 мс) | 11,1 с | пауза 0,65 + STT 2,4 + LLM 6,4 (шаг 1: первый токен 3,2 с; шаг 2 после инструмента до текста ещё ≈ 3 с) + TTS 1,6 + `play_gap` 0,09 |

Это два прогона на живой сети; медианы по ним считать нельзя, это иллюстрация, куда уходят секунды.

## 6. Выводы: куда уходят секунды (голосовая команда, стенд)

1. **LLM — 3–6 с**: ожидание первого токена 1,4–3,9 с (маршрутизация провайдера, не размер промпта); команда с инструментом — два последовательных запроса, до текста 6,4 с. 36 схем инструментов = ≈ 8,7 тыс. входных токенов на ход.
2. **STT — 2,4–2,7 с** для фразы 3,7–5,3 с (Google Speech v2, облако) + фиксированные 0,65 с тишины для определения конца. Groq Whisper: WAV 0,24 МБ → 3,4–7 с, Opus 11–16 КБ → ≈ 2,0 с.
3. **Новое соединение на каждый сервис** — 0,3–0,7 с TLS + RTT; для Edge — 1,8–5,5 с (WebSocket + токен) на **каждую фразу**: это был самый крупный и самый дешёвый для исправления кусок. Исправлено (раздел 3): первая фраза в паузе ≈ 0,6–0,8 с вместо ≈ 2,8 с.
4. **Пауза между кусками ответа**: синтез следующего предложения не начинается, пока играет предыдущее (по коду) — 0,6–0,9 с тишины на каждую границу даже с пулом.
5. Декодирование и старт воспроизведения — 50–100 мс; пренебрежимо.

Рекомендуемый порядок (оценка выигрыша — прикидка по замерам выше, не измерение):
1. (сделано) Edge keep-alive + прогрев: −1,5…−2,5 с на первую фразу после паузы, −2…−4 с на каждый следующий кусок. Чистка текста: перестаёт слать пустые запросы.
2. P-06/P-04: для прямых команд подтверждение по шаблону/кэшу фраз без LLM (−3…−6 с), короткая реплика-подтверждение параллельно основному запросу; уменьшить число схем инструментов (группы по требованию) — меньше токенов, меньше затрат; закрепление быстрого апстрима.
3. P-02: Opus/MP3 вместо WAV для Groq (−1…−2 с на слабой сети), потоковая отправка во время речи (−1…−2 с), конец фразы 650 → 450 мс (−0,2 с).
4. Предзагрузка следующего куска озвучки во время проигрывания предыдущего (−0,6…−0,9 с на границу).

### 8e. Группы инструментов по требованию: `tools_enable` (ветка tools2, 2026-10-30)

**Зачем.** Каждая показанная модели схема оплачивается на КАЖДОМ запросе. На master это 49 схем (47 встроенных + 2 демо-MCP стенда), 6 678 реальных токенов, больше, чем весь
системный текст. Теперь модели показывается **ядро + группы, которые нужны запросу**, остальное подключается само или вызовом `tools_enable`. Ни один инструмент не убран из реестра.

**Ядро** (показывается всегда): `app_open, app_state, speech_stop, note_create, memory_save, memory_get, memory_search, skill_view, skills_list, web_search`, все внешние MCP-инструменты

по своей инициативе, веб-поиск нужен для любого вопроса про свежие факты) либо он крошечный и нужен постоянно. Инструмент вне групп и вне ядра по умолчанию тоже ядро: новый инструмент
не пропадёт случайно (`ToolGroupsTest` при этом падает и требует решить, куда его отнести).

**Как выбираются группы** (`ToolRouter`, до первого запроса к модели; три независимых сигнала, любого достаточно):
1. слова запроса: основы русских слов с границей слова (`музык`, `файл`, `скриншот`, `забудь`, `навык`, `вчера` …; короткие латинские слова только целиком: `git` не срабатывает на «гитара»). Общие глаголы
   («включи», «открой», «запусти», «поставь», «выключи», «закрой») считаются, только если конкретных слов нет: «включи музыку» подключает `music`, а не заодно весь ADB; «включи Queen» открывает и плеер, и ADB;
2. липкость: инструменты из последних 3 пользовательских ходов беседы (берутся из самой истории, без нового состояния), уже выполненные для этого запроса вызовы прямой команды и ранее заказанные через `tools_enable` группы;
3. плеер играет или на паузе: подключается `music` («ну всё, надоело» без единого слова про музыку).
Намеренно с запасом: лишняя группа стоит 300–1400 токенов, а промах стоит запроса к модели или неверного ответа.

**Что делает цикл агента.** Список инструментов пересчитывается перед КАЖДЫМ шагом (`AgentLoop`), поэтому группа, включённая на шаге 1, показывается с шага 2. `tools_enable(groups)` отвечает сам цикл (в реестре его нет);
группы принимаются массивом или строкой, `all` включает всё, неверное имя возвращает исправимую ошибку со списком допустимых. Вызов скрытого инструмента **выполняется** (реестр знает все) и включает его группу
(даже если вызов не удался: модель увидит схему и поправит аргументы). Порядок схем равен порядку регистрации, `tools_enable` всегда последний: набор между шагами устойчив для кэша префикса.
Системный текст получил одну строку («часть инструментов скрыта… вызови `tools_enable`… не говори, что не умеешь, пока не проверил»), она входит в стабильный префикс.
Прямая команда (`phraseDirect`) показывает ядро + группу выполненного инструмента: модель лишь формулирует подтверждение. Настройки (страница «Настройки → Контекст и промпт»): `tools.groups` (по умолчанию включена; выключить = все инструменты на каждом ходу, как раньше) и `tools.fullEvery` (по умолчанию 0): каждый N-й запрос пользователя в чате несёт ВСЕ инструменты, как напоминание (при 5 это запросы 5, 10, 15 …; 1 = каждый запрос, то есть как до групп; 0 = никогда). Счёт тот же, что у напоминания правил: сообщения пользователя в чате, считая текущее, после «очистить контекст» заново; прямые команды («включи музыку») тоже считаются. Проверено на настоящем хранилище чата на ART (`ToolGroupsCheck`, строки `NEXT`).
Диагностика: журнал на каждый запрос («Инструменты: 13 из 49, группы: music (слово «музык»)»), трасса `llm.tool_specs` и `llm.tool_groups`, отчёт о промпте и MCP `agent_prompt_dump` показывают то, что реально уйдёт модели; `agent_tools_list` — группу каждого инструмента.

навыки, настройки, история, ядро); 8 реплик без инструментов («привет как дела», «что такое фотосинтез»…) дают ровно ядро и `tools_enable`. Тест проверен мутацией: убрана основа «яркост» → падает строка «увеличь яркость»;

* Полный голосовой ход «до звука» на эмуляторе или телефоне: сюда не входил ни CI-прогон, ни ADB. Влияние на время до звука судить можно только по замеру выше (прямой запрос к провайдеру), не по ходу целиком.
* Живая модель при промахе роутера: цикл (`tools_enable` → следующий шаг → вызов) проверен на mock-сервере; охотно ли настоящая модель вызовет `tools_enable`, а не ответит «не умею», на реальных ходах не измерялось.
  Роутер намеренно щедрый, чтобы на это почти не рассчитывать, но риск остаётся для запросов без характерных слов (например, свежий факт без слов «найди»/«погода» всё равно покрыт `web_search` из ядра).
* Провайдеры с жёстким кэшем префикса (Anthropic `cache_control`): набор инструментов теперь зависит от запроса, а инструменты идут в начало префикса, поэтому смена набора между ходами сбрасывает кэш этого префикса.
  Для `anthropic/*` это не измерялось; для DeepSeek автокэш и так срабатывал нестабильно (8b).
* MCP-серверы владельца: их прямые инструменты остаются в ядре, сколько бы их ни было; группировка для них не делалась.
* Самые тяжёлые схемы остались как были: `skill_manage` ≈ 990 токенов, `trigger_save` ≈ 370, `memory_save` ≈ 315 (последний в ядре, значит платится на каждом ходу). «Диета» их описаний не делалась.

## 9. Замеры speed3: сжатие загрузки, гедж, локальное обращение (P-02, P-03)

Стенд — Termux, Wi-Fi/сеть стенда; «стенд» = замер на этом телефоне. Телефон владельца в этой сессии недоступен по ADB, поэтому замеры ART сделаны через `app_process` в `tools/art-apk.sh`, которые работают на этом же телефоне без ADB.

### 9a. Кодирование на устройстве (ART, `EncoderCheck`, 8 с речи 16 кГц, 5 прогонов, стенд)
| формат | результат | байт | к WAV | время кодирования, мс (лучший / среднее / худший) |
|---|---|---|---|---|
| OGG/Opus 16 кбит/с | OggS, моно, 16 кГц (ffprobe: opus 48 кГц — внутренняя частота декодера) | 21 849 | 8,5 % | 446 / 644 / 1217 |
| FLAC | fLaC, 16 кГц | 90 476 | 35,3 % | 110 / 120 / 134 |
| WAV | RIFF (без кодирования) | 256 044 | 100 % | 0 |

Возможность кодеков (`MediaCodecList`): opus, flac — оба доступны; проверка заняла 116–121 мс один раз (кэшируется).
Цель «< 150 мс на 8 с»: **FLAC выполнена**, **Opus нет** (лучший прогон 446 мс). Первая попытка Opus не давала файл (откат в WAV, ~2 с на таймауте): исправлено общим циклом кодека и корректной записью в muxer; при этом цикл стал ждать 2 мс только тогда, когда кодек ничего не отдаёт.

Тесты `SttHedgeTest` (10 сценариев) и `AudioFormatTest` (9) зелёные. Отмена проигравшего — проверена флагом, а не на устройстве.

### 9d. Локальное обращение «Джарвис» (Vosk `vosk-model-small-ru-0.22`, `WakeCheck` на ART, стенд)
* Установка пакета: скачан из кэша `$TMPDIR`, SHA-256 и MD5 сошлись, установка 1,9 с, размер 87,1 МиБ.
* Загрузка модели: **1,2–1,6 с**; RSS +163…167 МБ (195 → 363 МБ); после выгрузки RSS 296 МБ (библиотеки остаются), модель выгружена.
* Декодирование: **26 мс на 1 с аудио** (RTF ≈ 0,026), 3,4 с на 132,7 с аудио.
* Фразы: **16 из 16** (восемь формулировок «Джарвис, …» × два голоса Edge: Светлана, Дмитрий). Вариант Дмитрия часто слышится как «джервис», и матчер его принимает.
* Ложные срабатывания на 22 не-обращениях (обычная речь, синтез Edge Svetlana/Dmitry; 26 фраз, часть не сгенерирована из-за ограничения Edge): локально **8 из 22** (36 %). Минимальная грамматика («джарвис» + [unk]) даёт те же 8 из 22, значит проблема не в словаре, а в том, что модель вынуждена выбирать из ограниченного набора.
* Подтверждение облаком (Groq, Opus, скрипт `build/meas/confirm.sh`, лог `build/meas/confirm.log`): **16/16** обращений подтверждены; из 8 локальных ложных срабатываний облако отвергло **7**; одно принято («Жарвис из соседнего отдела…» — фраза с похожим словом, написана намеренно). Итог конвейера на этом наборе: ложных принятий 1 из 22; загрузок в облако — только для локальных срабатываний (24 из 38 фраз), а не для каждой фразы.
* Задержка «обращение → детекция»: декодирование ≈ 80 мс на 3 с фразы + конец фразы `endSilenceMs = 650` мс → ≈ 0,73 с после последнего слова. **Цель < 700 мс не достигнута** на 30 мс; снижение конца фразы до 450 мс (план P-02) даст ≈ 0,53 с. Не менял: это общий `Segmenter`, задача P-02.
* Распознавание команды (`LocalStt`, полный словарь): «привет как дела у тебя сегодня» за 786 мс на 3,2 с; «включи музыку» из Dmitry-варианта не узнано (`совпадение 0%`) — модель уступает облаку, как и предупреждает её описание.

### 9e. Что изменилось в поведении
* Голосовой путь: обращение ищется локально, облако получает только фразы, где локально услышано обращение, и только для подтверждения и текста команды (до этого каждый звук 0,3–8,5 с уходил в облако, не больше 10 в минуту).
* Лимит 10 фраз в минуту теперь действует на все загрузки обращения.

### 9f. Не сделано и не измерено
* Фон: 22 не-обращения ≈ 1,5 мин речи, а не 10 минут, как в задании: Edge TTS отдаёт «NoAudioReceived» после ~20 запросов, а дневной объём не позволил дождаться. Частота ложных срабатываний по 10 минутам не измерена.
* Opus на Groq через кодер приложения: проверено на одной фразе; ElevenLabs Scribe с Opus не проверен (в коде только FLAC/WAV).
* Реальный микрофон, сеть мобильного оператора, Realme Note 50 — не измерялись (см. `docs/DEVICE_CHECKLIST_speed3.md`).

## 11. Исправление после замера speed4: формат загрузки по скорости, а не «всегда самый маленький»

Замер раздела 10 показал, что на быстрой сети `stt.format=auto` (всегда Opus) медленнее WAV на 350–480 мс: кодирование Opus (на телефоне 0,45–1,2 с на 8 с речи, большая часть — фиксированный запуск кодека) дороже экономии на отправке.
Теперь `auto` считает по каждой фразе время «кодирование + отправка» для WAV, FLAC и Opus при измеренной скорости отдачи (`UplinkMeter`: сглаженная оценка по прошлым загрузкам, без отдельного трафика) и выбирает самый быстрый.
Правило на примере фразы 3 с: ≥ 0,5 МБ/с — WAV; от ≈0,12 до 0,5 МБ/с — FLAC; ниже — Opus (на длинных фразах граница сдвигается в пользу Opus). Пока скорость не измерена — FLAC. Тесты: `AudioFormatTest` (таблица границ), `UplinkMeter` в нём же.
Ожидаемый выигрыш на быстрой сети: 0,3–0,5 с до звука; на слабой сети выбор остаётся Opus. Подтвердить на эмуляторе: `tools/ci/voice-bench.py` (ячейки DEFAULT/good до и после).
