## What exists (built by the lead, works)
GitHub mirror `artemjsdx/jarvis-android` (private) runs `.github/workflows/ci.yml` on every push to master: job `apk` (3 signed APKs, ~1.5 min), job `tests` (all JVM tests, ~5 min), job `emulator` (only with `[emu]` in the commit message or manual dispatch): Android 14 x86_64 emulator with KVM on a standard runner, installs the x86_64 build of the app, drives it through the MCP bridge with `tools/ci/emulator-smoke.sh`, publishes `emulator-report.zip` (screenshots of every screen from the live host, the headless host and `adb screencap`, `jv-check.txt`, `smoke.txt`, journal, logcat) as the release `ci-emulator`. APKs are published as the release `ci-apk` (Actions ARTIFACT storage of this account is full, so `upload-artifact` does not work; releases do).
You work with the helpers: `source tools/ci/gh.sh` (token stays inside the functions; NEVER print `$GH_TOKEN`, never write it anywhere), then `export CI_BRANCH=ci1`, `ci_push HEAD:refs/heads/ci1` (runs the secret scan first), `ci_run -f emulator=true`, `ci_watch 30`, `ci_logs`, `ci_fetch ci-emulator` (downloads into `build/ci-ci-emulator-ci1`; unzip and LOOK at the PNGs with the image reader). One emulator run takes ~8 minutes: plan experiments so that one run answers several questions. Never push to master (the lead merges your branch).

## Findings of the first emulator run (use them)
* `jv-check` OK (0 FAIL); `mcp-smoke`: 75 pass, 7 fail, 7 skip. The failures:
  1. `perf_trace/perf_summary` expects seeded turns (a JVM-fake feature) → on the real app there are none: make the scenario `jvm`-only or tolerate "no turns yet" (assert shape only).
  2. `sessions/sessions_delete` → `FORBIDDEN mcp.allowDestructive=false`: enable destructive tools ONLY in the emulator build: `tools/ci/build-bridge.sh emu` may add `"mcp.allowDestructive":"true"` to the provisioning JSON of the EMU apk (never of the phone apk).
  3. `tools_http/web_fetch reads the bridge's own /health`: the path `$.data.body` does not exist; the tool returns `text` (see docs/WEB_TOOLS.md).
  4. `tts_elevenlabs/voice_speak`: needs a key → add a `requires` mechanism to `tools/mcp-smoke.py` (`"requires": ["key:elevenlabs"]`, `["audio"]`, `["destructive"]`, `["seeded-turns"]`) so such scenarios SKIP with a stated reason instead of failing; the report must list skips with reasons.
  5. `ui_headless/ui_anim_probe` frames gt 10 (got 5): the emulator renders in software and is slow; lower the expectation to what is meaningful (frames advance: > 2) or scale by measured frame time.
  6. `ui_host/ui_wait tag=mcp.enabled` timed out: investigate (the page `settings/mcp` has a toggle; maybe it needs `ui_navigate {screen:"settings/mcp"}` first, or the tag differs) and fix the scenario or the missing tag in `McpPage`.
  7. `ui_settings/headless host says NOT_IMPLEMENTED`: stale since mcp4 → update the expectation.
* The adb screenshots showed the Android dialog **"System UI isn't responding"** (software GPU overload) on top of the app. Fix in `emulator-smoke.sh`: `adb shell settings put global hide_error_dialogs 1`, close system dialogs (`am broadcast -a android.intent.action.CLOSE_SYSTEM_DIALOGS`), give the emulator more resources (`cores: 2`, `ram-size: 3072M`, `heap-size: 576M` inputs of android-emulator-runner; the standard private-repo runner has 2 vCPU/7 GB), wait for idle before every screenshot (poll `perf_frames` or `adb shell dumpsys gfxinfo app.jarvis | grep "Janky"` or simply sleep until `top` CPU of system_server settles), and run the whole sequence twice: once with `ui.glass=full`(default auto) and once with `ui.glass=off` (set through the MCP tool `settings_set`), reporting `perf_frames` for both, so we learn what glass costs.
* The first screenshots showed ALL screens piled up: a real bug the emulator found (fixed by the lead in `Shell.navigate`, regression scene `ShellStackScenes`); after your first green run confirm in the PNGs that every screen now shows alone.
